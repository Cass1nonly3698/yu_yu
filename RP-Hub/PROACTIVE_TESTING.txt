修改前的四项分析
1. generateResponse() 如何构建和保存？
app.js 内的 generateResponse() 对已有聊天做预处理，解析世界书触发项，装配角色卡、开场白/示例、用户设定、启用的预设、UI 提示、历史与逐轮/二次压缩记忆；增强模式再做相关记忆召回。随后统一交给 requestTrackedChatCompletion()。流式/非流式都创建或追加真正的 assistant 气泡，finally 调用 saveChatHistoryNow()，由现有 scoped chat 存储写入 IndexedDB；正常完成后沿用自动记忆巡检。
2. 没有新增用户消息如何生成？
生成函数没有“必须先 push user”的前置条件。测试版直接调用 generateResponse(startTime, { proactive: ... })，在现有上下文完成后追加仅用于本次请求的 system 指令，说明没有新用户发言、现实间隔及主动联系目标。历史和输入框不插入用户消息，也不模拟发送按钮。原有流程本身以 user role 承载的角色设定/预设仍保持原逻辑；本功能不新增虚假的用户聊天或用户台词。
3. 原记忆是否支持连续 assistant？
普通连续 assistant 会合并，并归入前一个 user/assistant 轮；已有总结通过 assistant 来源 ID 命中后，后追加正文可能漏总结。因此新增主动消息使用 proactive=true 和 _preventContextMerge=true，保留独立 assistant 楼层。轮次快照为其建立 user=null 的独立轮；总结任务接受没有用户文本的主动轮，明确不得编造用户回应；逐轮压缩、二次压缩支持无 user 索引。旧普通轮次和旧记忆不迁移、不清空、不改写。
4. 如何防重复及跨分支写入？
主线/前台/聊天页/角色与分支加载完成/空闲守卫同时成立才显示提示。点击后马上占用页面锁与本次回访标记，并在独立 IndexedDB readwrite 事务中校验最后互动版本、间隔和当日额度后占用次数，避免同源多标签页重复抢占。请求前校验存储正文与当前页面正文是否一致，拒绝旧标签页。请求绑定角色 UUID、主线 scope、历史数组引用及角色切换 epoch；准备、召回、流式回调、响应完成均复查，保存固定的原主线 scope/history。切换沿用现有 stop/wait 协议，锁覆盖额度预占及保存阶段。

行为与配置
- 默认关闭。在“设置 → 记忆系统设置 → 角色主动消息（手动确认测试版）”启用。
- 间隔默认 2 小时，可调 2–168 小时；每日默认 3 次，可调 1–3 次。
- 每日按北京时间零点重置，所有角色合计；同一回访全局最多一次。
- 首次安装旧记录没有可靠的现实时间，不猜测旧时间，从首次观察开始记录。
- 正常主线发送、回复完成和主动回复完成会更新本地互动时间；支线不触发。
- 页面恢复、visibilitychange、pageshow（包括 Safari 返回缓存）只检查提示，不调用模型。
- 点击“老公有话想对你说 💌”才发起一次主模型请求。失败、取消也占次数，本次回访不自动重试，下一次也受间隔限制。切换等导致占额后未发请求时，保守保留占额。
- 主动请求沿用上下文/召回/保存流程，但暂不调用检索、联网、随机工具及其多轮续写；Gemini output_reply 抗截断仍保留，主动请求空回重试次数设为 1。普通请求仍保持原来的最多 3 次。
- 提示词要求结合剧情与性格主动开口，提供现实经过分钟数与北京时间；没有固定问候正文，也不把现实流逝强行等同于剧情时间。
- 配置单独保存在 localStorage 的 rp_hub_proactive_config_v1；互动与尝试次数单独保存在现有 IndexedDB store 的 rp_hub_proactive_v1。不会迁移、删除或重置聊天、角色、世界书或记忆。

iPhone Safari 手动验收（尚待实际设备执行）
1. 保留现有数据；建议先用项目原有导出功能留一份备份。用相同站点更新后的代码打开。
2. 先保持开关关闭，正常主线发送/刷新，确认原有聊天、角色、世界书和记忆正常。
3. 打开配置，保持 2 小时/3 次。主线发送并收到一条回复，离开 Safari 超过 2 小时。
4. 再打开页面：只应看到“老公有话想对你说 💌”，在点击前确认没有新的模型调用。
5. 点击一次：应只多一条 assistant 消息；内容应结合当前剧情，不出现伪造的用户发言。刷新后消息仍在。
6. 连点、马上刷新、短暂后台再返回：不得生成第二条。当天上限由自动测试覆盖；设备长测可累计三次回访后验证第四次无提示。
7. 在支线离开/回访，不显示提示；在生成、切换角色或分支期间不应触发。生成途中切换应停止原请求，返回原主线查看已收部分；新支线不能出现该消息。
8. 用测试 API 配置验证断网/错误响应；失败后不自动重试且无假用户消息；恢复网络后当前回访仍不能再次主动生成。
9. 保持原有 Safari Userscripts 北京时间注入脚本启用，查看上下文/请求的时间注入是否还在，验证流式和 Gemini 抗截断（如使用）。
10. 开启记忆后验证主动消息新增总结，原有总结仍在；主线/支线之间切换并刷新核对保存范围。

风险与限制
- 没有实际 iPhone Safari、真实模型接口或你的 Userscripts 脚本源码，不能声称已完成真机/脚本兼容验收。实现不替换 Date、fetch 或发送事件，也不移除已有注入；具体脚本的选择器/拦截方式仍需第 9 步确认。
- 某些模型代理不接受末尾 system 消息或没有新 user 的生成；此时按失败处理，绝不通过伪造用户发言降级。应使用支持此消息结构的现有接口。
- 浏览器本地存储被清理、系统时间跳变或更换站点/设备会影响互动时间及额度；不提供后台推送，Safari 挂起期间也不会生成。
- 刷新恢复已通过存储模块测试；实际浏览器配额/隐私模式等仍可能使原保存函数报错。保存失败时先处理页面提示，勿直接清空数据。
- 跨标签页额度抢占是事务性的，也会拒绝点击前已经过期的正文；原项目没有通用的跨标签页聊天编辑锁。不要在另一标签页同时编辑同一主线或发送普通消息，否则仍可能遇到原项目整段聊天保存的并发覆盖风险。
- 中途断网/取消时，沿用现有行为保留已收到的 assistant 部分并标记失败/中止；不会后台补写。额度保守计“尝试”，不是只计成功消息。
- 新增主动轮会让之后的轮次统计包含主动消息；旧普通消息和旧记忆没有数据迁移。旧版代码不理解主动轮标记，回滚后可能无法正确总结主动轮；完整原文仍保留。
- 本次仅手动确认测试版，没有自动调用模型的开关。先完成设备与实际模型验收，再讨论自动触发。
